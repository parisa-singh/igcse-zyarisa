The subject

What Computer Science is, at IGCSE

IGCSE Computer Science splits into two halves that need quite different kinds of revision. There's the theory side — hardware and processing, data representation, networks and communication, security, and the ethical and environmental impact of computing. And there's the problem-solving side — algorithm design, programming, and writing solutions in Cambridge's own pseudocode. You need to be comfortable switching between "explain how something works" answers and "write correct, precise pseudocode" answers, often in the same exam.

Where marks leak

Command-word pitfalls in Computer Science

"State" / "Identify"

These want one exact term — name the correct component, protocol, or data type — not a sentence describing it. Extra waffle doesn't earn extra marks, and a vague near-miss usually scores zero.

"Describe" vs "Explain"

Describe wants what happens, step by step. Explain wants why it happens, with reasoning or a cause-effect link. Answering an "explain" with only a description leaves the reasoning marks on the table.

"Write" / "Complete an algorithm"

This means real Cambridge pseudocode, following their exact conventions — not "code-ish" English and not Python syntax. See the pseudocode reference below before you sit any programming question.

The specific stuff

CS tips that actually move marks

Trace tables — drill them specifically

A trace-table question appears every single year. Practise working through an algorithm row by row, updating each variable exactly when the algorithm says to — not when it "feels" like it should change.

Design in English first, then translate

Don't try to write pseudocode straight out of your head. Sketch the logic in plain English or a flowchart first, then convert it line by line into correct pseudocode. It's faster and far less error-prone.

Testing needs three kinds of data

Any validation question wants normal, boundary, and erroneous test data. Missing one of the three is one of the most common ways to drop easy marks on test-plan questions.

Use the exact technical term

Theory marks live and die on precision: validation is not verification, a compiler is not an interpreter. Close-but-wrong terminology scores nothing, even if you clearly understand the concept.

Learn it exactly

Pseudocode reference

Cambridge's pseudocode conventions are effectively their own mini-language, and the mark scheme is strict about following them precisely — so it's worth learning them properly rather than winging it in the exam.

The core rules

  • Keywords in UPPERCASE: IF, THEN, ELSE, ENDIF, FOR, TO, NEXT, WHILE, DO, ENDWHILE, REPEAT, UNTIL, PROCEDURE, ENDPROCEDURE, FUNCTION, RETURN, INPUT, OUTPUT, AND, OR, NOT, DIV, MOD
  • Identifiers in PascalCase: NumberOfPlayers, TotalScore, UserName
  • Assignment uses ←, never =: Count ← Count + 1
  • String literals in double quotes: "Hello"
  • Comments start with // and run to the end of the line
  • Arrays are 1-indexed: MyArray[1:10] holds elements 1 through 10, not 0 through 9
Common pseudocode errors that lose marks

Writing keywords in lowercase (if instead of IF); using = for assignment instead of ←; confusing WHILE (checks before each loop) with REPEAT...UNTIL (checks after); off-by-one errors from forgetting arrays start at 1, not 0; and forgetting to close a structure with ENDIF, ENDWHILE, or ENDPROCEDURE.

Worked example — linear search

PROCEDURE LinearSearch(Numbers, Target)
   Found ← FALSE
   Index ← 1
   WHILE Index <= 10 AND Found = FALSE DO
      IF Numbers[Index] = Target THEN
         OUTPUT "Found at position ", Index
         Found ← TRUE
      ENDIF
      Index ← Index + 1
   ENDWHILE
   IF Found = FALSE THEN
      OUTPUT "Not found"
   ENDIF
ENDPROCEDURE

Other algorithms worth being able to write from memory in pseudocode: bubble sort, linear search, binary search, totalling, counting, and finding a maximum or minimum value.
